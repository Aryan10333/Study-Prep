# 03_advanced_rag: Advanced Retrieval-Augmented Generation (RAG) Syllabus

## 1. Context & Alignment
* **Profile Focus:** AI Engineer / Applied AI SDE-2/SDE-3 (Aryan Chandra). The candidate has already shipped production RAG (hybrid BM25 + vector retrieval, chunking, reranking, metadata extraction) at Jio Platforms, so this topic is scoped to go *beyond* that baseline — deep internals of indexing/retrieval trade-offs, GraphRAG, Agentic RAG, formal evaluation, and the production hardening (caching, security, multi-tenancy) that differentiates a senior-level RAG system from a first working prototype.
* **Interview Frequency:** Extremely High. RAG system design is one of the single most common deep-dives across AI Engineer, Applied AI Engineer, MLE, and AI Platform Engineer screens — both as a dedicated system-design round and as a recurring thread through behavioral/project-deep-dive rounds.
* **Core Goal:** Master the full production RAG lifecycle — document processing, chunking, and ongoing document/index lifecycle management, embedding and vector indexing internals, hybrid retrieval and reranking, query understanding, GraphRAG, Agentic/self-correcting RAG loops, a systematic methodology for debugging a bad answer back to its root pipeline stage, formal evaluation frameworks (RAGAS-style), and the observability/caching/security/multi-tenancy/scalability concerns of running RAG as a real product, not a notebook demo.

## 2. Module Chapters & Conceptual Scope
These chapters outline the sequential topics to be covered:

- **Module 01: RAG Fundamentals & Production Architecture Patterns**
  - *Key Concepts:* Why RAG (vs. fine-tuning vs. long-context, and when to combine them), the naive RAG pipeline (ingest → chunk → embed → index → retrieve → generate) and its failure modes, Advanced RAG architecture patterns (pre-retrieval / retrieval / post-retrieval stages), and a **concrete Long Context vs. RAG decision framework** with an explicit criteria checklist — **corpus size, freshness/update frequency, query frequency (volume), latency budget, cost, required retrieval accuracy, and reasoning requirements** (single-hop lookup vs. multi-document/multi-hop synthesis) — backed by a quantified cost-crossover calculation, not a purely qualitative choice.
  - *System Bottlenecks & Focus:* End-to-end latency budget across the pipeline, staleness vs. cost of re-indexing, and the "garbage in, garbage out" failure surface of naive RAG.

- **Module 02: Document Processing, Chunking & Document Lifecycle Management**
  - *Key Concepts:* Document parsing (PDF/HTML/structured docs, layout-aware parsing), fixed-size vs. recursive vs. semantic chunking, parent-child (small-to-big) chunking, sliding-window overlap, and **Late Chunking as a first-class technique** — embedding the *full* document first with a long-context embedding model so every token's representation is computed with the whole document as context, *then* pooling token-level representations into per-chunk vectors afterward; explained specifically through *why* this preserves cross-chunk semantics that standard chunk-then-embed pipelines structurally lose (a chunk embedded in isolation has no representation of what came before/after its boundary, while a late-chunked vector is pooled from representations that already "saw" that surrounding context) — no deep mathematical treatment required, this is an architectural/intuition explanation. Also covers metadata extraction/enrichment for filtered retrieval. **Production document lifecycle**, taught end-to-end through one worked example document tracked across its full lifecycle (added → incrementally indexed → edited/versioned → re-indexed → detected stale → deleted/tombstoned): incremental index updates, document deletion/tombstoning, re-indexing strategy, content versioning, and stale-embedding detection (when a source document changes but its index entry doesn't reflect the edit yet).
  - *System Bottlenecks & Focus:* Chunk-size vs. retrieval-precision trade-off, context fragmentation across chunk boundaries, ingestion pipeline throughput at document-corpus scale, and the operational cost of keeping a live index consistent with a constantly-changing source corpus (update/delete lag, orphaned stale entries).

- **Module 03: Embeddings for Retrieval & Vector Representations**
  - *Key Concepts:* Dense embedding models (bi-encoders) vs. cross-encoders, embedding model selection (dimensionality, domain fit, multilingual support), Matryoshka Representation Learning and embedding truncation, and embedding fine-tuning for domain adaptation. Builds directly on `00_nlp_fundamentals`' classical embeddings (Word2Vec/GloVe/FastText, not re-covered here) and BM25 (Module 05's sparse-side baseline).
  - *System Bottlenecks & Focus:* Embedding dimensionality vs. index storage/query-latency trade-off, and embedding drift when the domain shifts from the model's training distribution.

- **Module 04: Vector Indexing, ANN Search & Vector Database Internals**
  - *Key Concepts:* Approximate Nearest Neighbor (ANN) search; HNSW graph construction and search mechanics **with worked numerical intuition for its key parameters** ($M$ = max connections per node and its direct effect on graph memory/recall, `efConstruction`/`efSearch` and their effect on build quality vs. query latency); IVF (Inverted File Index) **with a small worked example of `nlist`/`nprobe` cluster-count trade-offs** (how many clusters to scan vs. total clusters, and its recall/latency consequence); IVF-PQ (Product Quantization) **with a small worked compression-ratio calculation** (splitting a vector into subvectors, quantizing each to a small codebook, and computing the resulting bytes-per-vector vs. raw float storage); exact vs. approximate recall trade-offs; and vector database architecture (Pinecone, Weaviate, Qdrant, Milvus) — sharding, filtering, and hybrid metadata queries. Closes with an explicit **parameter-to-effect drill**, not just definitions: `nlist` vs. `nprobe` and $M$ vs. `efSearch` presented side-by-side against what happens to **recall, latency, and memory** as each is tuned up or down — the goal is being able to reason live about "if I double `nprobe`, what happens to my p99 latency and recall," not just recite what each parameter means.
  - *System Bottlenecks & Focus:* Recall-vs-latency-vs-memory trade-off curve, index build time at scale, and the compute/storage cost of re-indexing on corpus updates.

- **Module 05: Hybrid Retrieval & Reranking**
  - *Key Concepts:* Sparse (BM25, from `00_nlp_fundamentals`) + dense hybrid fusion (Reciprocal Rank Fusion), cross-encoder reranking, ColBERT-style late-interaction retrieval, and multi-stage retrieve-then-rerank pipelines. Explicitly teaches the **candidate-set sizing funnel** as its own topic: initial retrieval Top-K → RRF fusion → rerank down to Top-N → final assembled context Top-M — walked through with concrete numbers at each stage, explaining *why* widening any stage improves recall (more real candidates survive to the next stage) while directly increasing latency/cost (more documents fetched, scored, or fed to the generator). Includes an explicit **"when reranking isn't worth it"** section (small candidate sets, tight latency budgets, or a first-stage retriever already precise enough that the added cross-encoder pass buys negligible precision).
  - *System Bottlenecks & Focus:* Reranking latency cost vs. precision gain, candidate-set size tuning (top-k retrieved → top-n reranked) at each funnel stage, and when hybrid search outperforms dense-only retrieval.

- **Module 06: Query Understanding, Transformation & Optimization**
  - *Key Concepts:* Query expansion and rewriting, HyDE (Hypothetical Document Embeddings), query decomposition for multi-hop questions, multi-query retrieval, and semantic routing across multiple retrieval sources/indexes. Each technique closes with an explicit **"when NOT to use this"** note — e.g., HyDE and query rewriting add a full extra LLM call to every query's critical path, which is hard to justify when queries are already short/well-formed and the retriever handles them fine unmodified; the interview-relevant skill is recognizing when the added latency/cost of query transformation isn't buying a meaningful retrieval-quality improvement.
  - *System Bottlenecks & Focus:* Added latency/cost of query-transformation LLM calls, and failure modes where query rewriting drifts from user intent.

- **Module 07: GraphRAG & Structured/Knowledge-Graph Retrieval**
  - *Key Concepts:* Knowledge graph construction from unstructured text (entity/relation extraction), graph-based retrieval and community detection/summarization (Microsoft GraphRAG-style), and when graph retrieval outperforms flat vector retrieval (multi-hop, "global" corpus-level questions). Includes an explicit **"when NOT to use GraphRAG"** section — graph construction is expensive and goes stale as the corpus changes, so it's a poor fit for small corpora, high-update-frequency content, or workloads dominated by simple single-hop lookups where flat vector/hybrid retrieval (Module 05) already performs well at a fraction of the setup and maintenance cost.
  - *System Bottlenecks & Focus:* Graph construction cost and staleness, and the local (entity-level) vs. global (corpus-summary) query trade-off.

- **Module 08: Agentic RAG & Self-Correcting Retrieval Loops**
  - *Key Concepts:* Agentic RAG (LLM-driven retrieval tool-calling instead of a fixed pipeline), Self-RAG and Corrective RAG (retrieval-quality self-critique and re-retrieval), iterative retrieve-generate-verify loops, and multi-agent retrieval (specialized retriever agents per source/domain). Includes an explicit **"when NOT to use Agentic RAG"** section — the iterative loop's unbounded latency/cost is rarely justified for queries a single well-tuned retrieve-then-generate pass already answers correctly; it earns its cost specifically on queries where the first retrieval attempt is plausibly wrong or incomplete and re-retrieval can measurably fix it.
  - *Scope Discipline:* This module teaches **retrieval-specific agent loops only** — the mechanics of an agent deciding to retrieve, critique retrieval quality, and re-retrieve. General agent architecture, MCP (tool-calling protocol internals), and multi-agent orchestration patterns are owned by the dedicated AI Agents topic and are cross-referenced here, not re-taught, matching Module 09's same scope-discipline principle applied to evaluation/observability.
  - *System Bottlenecks & Focus:* Unbounded latency/cost from iterative agent loops, and the need for explicit loop termination/budget guards in production.

- **Module 09: RAG Evaluation, Debugging & Production Hardening**
  - *Key Concepts:* Retrieval metrics (Recall@k, MRR, NDCG), generation metrics (faithfulness, answer relevancy, context precision/recall — RAGAS-style), LLM-as-judge evaluation pitfalls; a **systematic RAG debugging methodology** for isolating which pipeline stage actually caused a bad answer — query → chunking → embedding → retrieval → reranking → context assembly → generation — with a concrete diagnostic check at each stage (e.g., "is the right chunk even in the index?" vs. "was it retrieved but ranked low?" vs. "was it retrieved but dropped/truncated from context?" vs. "was it in context but the generator ignored it?"); **retrieval observability** (logging the query itself, retrieved document/chunk IDs, retrieval scores, reranker scores, Top-K, retrieval latency, and empty/low-quality-retrieval rates as the concrete telemetry that makes the debugging methodology actually usable in production, not just conceptual); semantic caching; RAG-specific security (prompt injection via retrieved content, data leakage across tenants); multi-tenant index isolation; and production scaling (sharding, read replicas, cost/latency SLOs).
  - *Scope Discipline:* This module stays **RAG-specific**. General LLM-as-judge theory, broader agent evaluation methodology, and general LLMOps observability/monitoring patterns are each owned by their own dedicated topics and are cross-referenced here, not re-taught — this module only covers what's genuinely specific to a retrieval pipeline (retrieval-stage metrics, retrieval-stage telemetry, retrieval-stage debugging).
  - *System Bottlenecks & Focus:* Evaluation metric noise/bias, cache-hit-rate vs. staleness trade-off, the blast radius of a single-tenant data leak in a shared vector index, and the tooling/telemetry cost of maintaining stage-level observability across a multi-stage pipeline at scale.

Module 10 (Interview Q&A track, generated separately per `interview_qa_generator/SKILL.md`) will cover standalone screening questions across all nine modules above.
