## 2. Module Chapters & Conceptual Scope
These chapters outline the sequential modules to be created under the `modules/` directory:

- **Module 01: Agent Fundamentals & Reasoning Patterns**
  - *Key Concepts:* What makes a system "agentic" (dynamic, model-driven control flow) vs. a fixed pipeline; ReAct (Reason + Act interleaving) as the foundational pattern; Chain-of-Thought vs. agentic reasoning; plan-and-execute vs. purely reactive agents. Closes with a **formal "when NOT to use agents" decision framework**: a structured comparison of **a single LLM call vs. a deterministic workflow vs. a single agent vs. a multi-agent system**, evaluated explicitly against complexity, cost, latency, reliability, and controllability — not a vague "agents are powerful" default, a concrete checklist for picking the least complex architecture that actually satisfies the task's real requirements (cross-referencing `03_advanced_rag` Module 08's Agentic RAG as the retrieval-specific instance of this general pattern).
  - *System Bottlenecks & Focus:* Latency/cost of multi-step reasoning loops, non-determinism in agent trajectories, and the risk of unbounded reasoning cycles without explicit stopping criteria.

- **Module 02: Tool Calling & Function Calling Internals**
  - *Key Concepts:* LLM function-calling mechanics — tool schema definition, how a model selects which tool to call and with what arguments, and **how tool naming, description quality, required vs. optional parameter design, overall schema quality, and the total number of available tools directly affect tool-selection accuracy** (too many similarly-described tools, or ambiguous/overloaded parameter design, measurably degrades selection). **Safe parallel vs. sequential tool execution** — which operations are safe to parallelize (read-only, independent) vs. which must run sequentially (dependent, side-effecting), including the general dependency-analysis principle this module establishes and Module 06 later applies at the agent level. **Idempotent tool execution** for tools with real-world side effects: idempotency keys to prevent duplicate actions on retry, confirmation gates before irreversible actions, and safe-retry design. Closes with a **simple per-task cost/latency model**: composing sequential vs. parallel tool-call latency and per-call token cost into an estimate of a task's total expected cost.
  - *System Bottlenecks & Focus:* Schema design's direct effect on tool-selection accuracy, tool-call latency stacking in multi-tool-call turns (sequential vs. parallelizable), and the cost of re-sending full conversation history on every tool round-trip.

- **Module 03: Model Context Protocol (MCP) & Agent-Tool Standardization**
  - *Key Concepts:* Why MCP exists — standardizing agent-to-tool/resource integration instead of every application writing bespoke tool-calling glue; MCP's architecture (client-host-server model, the Tools/Resources/Prompts primitives); **local vs. remote MCP servers** and their differing trust/latency/deployment profiles (a local stdio server running with the host's own privileges vs. a remote SSE/HTTP server operated by a third party); **capability discovery** (how a client learns what tools/resources/prompts a server actually exposes at connect time); **versioning** (protocol version negotiation and backward compatibility as MCP evolves); **authentication/authorization and tool-level permissions** (how a client authenticates to a server, how access is scoped, and how individual tools within a server can carry their own narrower permission grants); and the **security risks of exposing powerful tools** through an MCP server — an MCP server is a new, real attack surface, not just a convenience layer, and a remote or third-party server is a meaningfully larger trust boundary than a local one. Compares MCP against native LLM function-calling and framework-specific tool abstractions (LangChain tools).
  - *System Bottlenecks & Focus:* Protocol overhead vs. native function-calling, and the security surface of exposing real tools/resources through an MCP server to a model-driven client.

- **Module 04: Context, State & Memory for Agents**
  - *Key Concepts:* An explicit **three-way Context vs. State vs. Memory distinction** as the module's organizing concept — the single most commonly conflated set of terms in agent system design: **context** is the actual information sent to the model on a given call (the assembled prompt — system instructions, tool schemas, retrieved memory, and whatever state is relevant to this turn — everything the model can literally see right now); **state** is the information required to execute or resume the current workflow — often ephemeral or checkpointed, scoped to one run, and owned by the orchestration layer (Module 05); **memory** is information *intentionally* persisted across interactions/sessions, deliberately written and retrieved rather than automatically carried forward. Context is the projection point where relevant state and retrieved memory both get assembled into what the model actually sees on a given turn — the three concepts compose, they aren't independent layers. Covers short-term memory (conversation buffer, sliding window) vs. long-term memory (persisted across sessions); episodic vs. semantic memory; vector-store-backed long-term memory as a RAG-adjacent retrieval problem (cross-referencing `03_advanced_rag`'s embedding/indexing modules rather than re-deriving them); memory summarization/compression strategies for staying within context budget; and memory write policies (what gets remembered, and when).
  - *System Bottlenecks & Focus:* Context-window budget vs. memory-recall completeness trade-off, and memory staleness/consistency as an agent runs across many turns or sessions.

- **Module 05: Agent Orchestration, State Machines & Durable Execution**
  - *Key Concepts:* Graph-based agent orchestration (nodes, edges, shared state) as a more explicit and debuggable alternative to an implicit reasoning loop; conditional routing between nodes; cyclic graphs for iterative agent behavior; human-in-the-loop interrupts (pausing execution for approval before a sensitive action). **Durable execution as a first-class, deeply-covered topic**: **checkpointing** (persisting state at each step); **crash recovery** (what a workflow needs to survive an unexpected process/node failure mid-run); **resume** (continuing a workflow from its last good checkpoint rather than restarting from scratch); **workflow-level idempotency** (re-running a resumed step without duplicating its effects — distinct from, and building on, Module 02's tool-level idempotency); **pause/resume** for human-gated or scheduled workflows; and the specific demands of genuinely **long-running workflows** (multi-hour/multi-day agent tasks where the process itself may not stay alive the whole time). Comparison against simpler linear chain/pipeline orchestration and when the added state-machine/durability complexity is actually justified.
  - *System Bottlenecks & Focus:* State management complexity as graphs grow, debuggability of non-deterministic graph execution paths in production, and the storage/latency cost of checkpointing on every step of a long-running workflow.

- **Module 06: Multi-Agent Systems & Coordination Patterns**
  - *Key Concepts:* Orchestrator-worker (supervisor) patterns vs. peer-to-peer agent communication; agent specialization/role design (why splitting responsibilities across specialized agents can outperform one generalist agent, and why it sometimes doesn't); coordination and hand-off mechanics between agents. **Safe parallel vs. sequential agent execution** — the same dependency-analysis principle Module 02 establishes for individual tool calls, applied one level up: independent sub-agents/sub-tasks with no shared-state dependency can run concurrently, while agents whose output feeds another agent's input must run sequentially. Applies Module 01's formal decision framework specifically to the single-agent-vs-multi-agent boundary, rather than re-deriving a separate "when NOT to use multi-agent" argument from scratch.
  - *System Bottlenecks & Focus:* Coordination overhead, emergent failure modes that only appear across agent boundaries (miscommunication, redundant work), and the direct cost multiplication of running several agents instead of one.

- **Module 07: Agent Frameworks Landscape**
  - *Key Concepts:* A comparative survey of the major agent frameworks — LangGraph (graph-based, the candidate's own production stack), AutoGen (conversational multi-agent), CrewAI (role-based multi-agent), and OpenAI's Agents SDK/Assistants API (provider-native) — kept deliberately **conceptual, not API-tutorial**, comparing each framework along six stable dimensions: **architecture** (graph/conversational/role-based/provider-native), **control** (how much explicit control flow the framework gives you vs. how much it decides for you), **state** (how each framework represents and persists state — direct application of Module 04's/05's own concepts), **observability** (how easy each makes it to trace/debug a run), **extensibility** (how easily custom tools/agents/logic plug in), and **lock-in** (how much of your code becomes framework-specific and hard to port). When to build a custom agent loop vs. adopt a framework, evaluated against these same six dimensions.
  - *System Bottlenecks & Focus:* Framework lock-in risk, abstraction leakage when a framework's assumptions don't fit a real use case, and the added difficulty of debugging agent behavior through a framework's own orchestration layer.

- **Module 08: Agent Evaluation & Debugging**
  - *Key Concepts:* Agent-specific evaluation beyond single-turn LLM eval, built around concrete, **quantitative metrics**: task success rate, tool-selection accuracy (right tool chosen), tool-argument accuracy (right arguments passed), **tool failure rate** (how often a called tool itself errors out, independent of whether the *right* tool was chosen), **retry rate** (how often the agent needs a second attempt at a step, a distinct signal from outright tool failure), trajectory efficiency (steps actually taken vs. the minimum needed, as a ratio) and **steps per successful task** (the same idea as a raw, directly-comparable count rather than a ratio), and **cost per successful task** (tying directly back to Module 02's per-task cost model, but now measured, not estimated). Full trajectory evaluation (not just the final output), LLM-as-judge applied to agent trajectories and its specific pitfalls, and agent observability/tracing (Langfuse-style, matching the candidate's own production stack). A systematic methodology for common agent failure modes — infinite/repeating loops, tool misuse, planning failures, premature termination.
  - *Scope Discipline:* This module owns general agent evaluation methodology and trajectory-level debugging. RAG-specific retrieval-stage debugging remains owned by `03_advanced_rag` Module 09 and is cross-referenced, not re-taught; general single-turn LLM evaluation and inference-serving performance concerns are likewise out of scope, owned by their own dedicated topics.
  - *System Bottlenecks & Focus:* Evaluation cost at full-trajectory granularity (every step, not just the final answer), and the non-reproducibility of agent runs complicating regression testing.

- **Module 09: Production Agent Systems, Safety & Security**
  - *Key Concepts:* Guardrails and permission boundaries — what actions an agent can take fully autonomously vs. what requires human approval (the production policy layer built on Module 02's confirmation-gate mechanics); rate limiting and hard cost/step budgets to bound an agent's own runaway behavior (the production enforcement of Module 02's cost model). **Agent security in depth**: **indirect prompt injection** — malicious instructions that arrive not from the user, but from content the agent processes as data and ends up treating as instructions, from any of several real sources: **tool outputs** (a fetched webpage or API response), **retrieved content** (a poisoned document surfaced by RAG, cross-referencing `03_advanced_rag`'s own prompt-injection coverage rather than duplicating it), **files** (an uploaded or read document containing hidden instructions), or **external APIs** (a third-party response crafted to hijack the agent). Mitigation is covered as a layered set of controls, not one silver bullet: **isolation** (sandboxing tool/content execution so untrusted content can't directly act), **validation** (checking/sanitizing untrusted content before it enters context), **least-privilege tool access** (scoping each agent/tool to the minimum permissions it needs, so even a successful injection has limited blast radius), **approval gates** (requiring human confirmation before a sensitive action executes, the same confirmation-gate mechanic from Module 02 applied as a security control), and **auditing** (recording every action taken for after-the-fact review and incident response). Also covers **authorization boundaries** (per-agent, per-tool, per-action permission scoping) as the structural mechanism least-privilege access is built on. Deployment patterns (synchronous request/response agents vs. long-running async/background agents, building on Module 05's durable execution).
  - *System Bottlenecks & Focus:* The blast radius of an agent with real-world tool access (a bad decision can now take a real action, not just generate bad text), and enforcing latency/cost budgets on an inherently variable-length process.

**Cross-module boundary discipline (applies throughout):** RAG-specific retrieval, chunking, embedding, and indexing details remain owned by `03_advanced_rag` and are cross-referenced, not duplicated, here — this topic covers the *agent* layer (reasoning, tools, memory, orchestration, multi-agent, evaluation, safety), not retrieval mechanics. General single-turn LLM evaluation methodology and LLM inference-serving/optimization concerns are likewise cross-referenced to their own dedicated topics where relevant, not re-taught here.

Module 10 (Interview Q&A track, generated separately per `interview_qa_generator/SKILL.md`) will cover standalone screening questions across all nine modules above.
