# Context Engineering, A2A & Agent Supply-Chain Security Syllabus

## 1. Context & Alignment
* **Profile Focus:** A gap-filler topic built from 2026 hiring and industry signals. AI engineering has shifted from "build an agent" to "engineer the harness around it": what goes into the context window, how it is cached and compacted, how agents talk to other agents, and how the tools they load are secured. The candidate already runs LangGraph agents and RAG in production, so this topic targets the next layer up: the decisions that separate a demo agent from a long-running, cost-controlled, secure one. It builds directly on `04_ai_agents_and_protocols`, `05_prompt_engineering_and_structured_generation`, `06_llm_inference_and_optimization` and `08_genai_system_design_and_llmops`, and covers only what those topics don't.
* **Interview Frequency:** High and rising. Common prompts: "How do you manage context for an agent that runs for hours?", "Prompt caching vs summarization: when would you pick each?", "Why does accuracy drop with long context even when the answer is in it?", "How do MCP and A2A differ?", and "How would you stop a malicious MCP server from hijacking your agent?" Especially frequent at foundation-model companies (OpenAI, Anthropic), agent and coding-tool startups (Cognition, Sierra, Glean, Poolside), and enterprise AI platforms (Salesforce, ServiceNow, Atlassian).
* **Core Goal:** Treat context as an engineered, budgeted and priced resource, with a measurable quality curve, a cache-aware layout and a deliberate compaction policy. Know A2A well enough to design a cross-organization agent integration. Be able to threat-model and secure an agent's tool supply chain (MCP servers, skills, plugins) end to end.

## 2. Module Chapters & Conceptual Scope

- **Module 01: Context Engineering as a Discipline**
  - *Key Concepts:* Context engineering vs prompt engineering: the unit of design moves from "the instruction" to "everything the model sees at each step" (system prompt, tool definitions, retrieved content, conversation history, memory, scratchpad). The four core operations: **write** (persist outside the window), **select** (pull in just in time), **compress** (summarize or trim), and **isolate** (split across sub-agents or sandboxes). Context as a budget measured in tokens, latency and dollars, with tool definitions as a frequently overlooked fixed cost (dozens of MCP tools can consume thousands of tokens before the first user turn). Static vs dynamic context, and why the order of the two matters for caching (Module 03).
  - *System Bottlenecks & Focus:* Every token is paid for on every step of an agent loop. A 20-step agent with a 30k-token context processes 600k input tokens. The focus is the per-step context bill and how each of the four operations changes it.

- **Module 02: Context Rot & Long-Context Degradation**
  - *Key Concepts:* Why accuracy falls as context grows, even when the relevant fact is present. Separate from the position bias ("lost in the middle") covered in `05` Module 06, the causes are attention dilution, distractors that are semantically close to the answer, and multi-hop reasoning across distant spans. Advertised vs effective context length. Why needle-in-a-haystack scores overstate real capability, and what harder benchmarks (RULER-style multi-needle, aggregation and multi-hop tasks) show instead. How to measure the degradation curve for your own model and your own task, and how to set a context ceiling from it.
  - *System Bottlenecks & Focus:* A larger context window is not free capacity. The focus is turning "the model supports 1M tokens" into a measured, task-specific usable limit, then designing selection and compaction to stay under it.

- **Module 03: Prompt Caching & Cache-Aware Context Layout**
  - *Key Concepts:* What provider-side prompt caching changes in practice, building on the prefix and KV-cache mechanics in `06_llm_inference_and_optimization` without re-deriving them: cached-read discounts, cache-write premiums, TTLs, minimum cacheable lengths and explicit cache breakpoints. Cache-aware layout: stable content first (system prompt, tool definitions, long documents), volatile content last. Common cache-busters: timestamps in the system prompt, re-ordered tool lists, per-request IDs. **The central trade-off:** keeping the full history (cheap to re-read once cached, nothing lost) vs compacting it (fewer tokens, but every summarization rewrites the prefix and invalidates the cache). Includes a hand calculation of the break-even point.
  - *System Bottlenecks & Focus:* Cost and time-to-first-token of long-running agents. A worked example shows that with caching, keeping everything can beat summarizing on cost, latency and recall up to a measurable length, and that compaction should be a deliberate, triggered decision rather than a default.

- **Module 04: Agent Harness & Long-Running Loop Design**
  - *Key Concepts:* The harness as the system around the model: the loop, tool registry, permission layer, context manager, state store and stop conditions. **Instruction and memory files** (`AGENTS.md` / `CLAUDE.md`-style project instructions and agent-written notes files) as durable, versioned, human-editable context. **Progressive disclosure:** loading tool and skill details only when needed instead of up front. Just-in-time retrieval (file paths, queries and handles in context, contents fetched on demand) vs pre-loading. Sub-agent isolation as a context-engineering tool: clean windows, condensed results and the token-cost multiplier (multi-agent setups reported at roughly 15x the tokens), building on `04` Module 06's orchestration content. Long-horizon patterns: compaction plus structured notes, checkpoint and resume (referencing `04` Module 05's durable execution), and human "outer loop" supervision of an autonomous inner loop.
  - *System Bottlenecks & Focus:* Agents that run for hours or across many sessions without losing the plot. The focus is the design choices (what persists, what is summarized, what is isolated, where a human checks in) that keep quality stable as task length grows.

- **Module 05: A2A Protocol & Agent Interoperability**
  - *Key Concepts:* The A2A (Agent2Agent) protocol: agent cards and capability discovery, the task lifecycle (submitted → working → input-required → completed/failed/canceled), messages vs artifacts, streaming and push notifications for long tasks, and authentication schemes declared in the agent card. **MCP vs A2A:** MCP connects an agent to tools and data (the agent stays in control); A2A connects an agent to another agent that keeps its own reasoning, state and tools (an opaque peer across a trust boundary). Both are now governed by Linux Foundation bodies rather than a single vendor. When to expose a capability as an MCP tool, as an A2A agent, or as plain HTTP, and when multi-agent interop is unnecessary overhead.
  - *System Bottlenecks & Focus:* Integrating agents owned by different teams or companies: discovery, latency of long-running delegated tasks, failure and cancellation semantics, and trust. The focus is the protocol boundary, not internal orchestration, which is owned by `04`.

- **Module 06: Agent Supply-Chain Threats**
  - *Key Concepts:* Why 2026 agent security is a supply-chain problem first and a prompt-injection problem second. Threat catalog: **malicious MCP servers and skills** (code that runs with the agent's privileges), **tool poisoning** (hidden instructions inside tool descriptions or schemas that the model reads but the user never sees), **rug pulls** (a tool's definition changing after it was approved), **tool shadowing** and name collisions across servers, typosquatted packages, **exposed unauthenticated MCP servers**, the confused-deputy problem, and token passthrough. Mapping these to the **OWASP Top 10 for LLM Applications** (prompt injection, sensitive information disclosure, supply chain, excessive agency and others) and to OWASP's agentic-threat guidance. Covers direct and indirect injection only where it connects to the supply chain, since the general defenses are owned by `04` Module 09 and `05` Module 08.
  - *System Bottlenecks & Focus:* The attack surface grows with every tool an agent loads, and a single malicious tool description can steer an agent that holds legitimate credentials. The focus is threat-modeling a real agent's tool set and naming the specific risk at each point.

- **Module 07: Securing the Agent Tool Supply Chain in Production**
  - *Key Concepts:* Defenses mapped one-to-one to Module 06's threats. **Registries and allowlists** (only approved servers and skills load). **Pinning and hashing tool definitions** so a changed description triggers re-approval (rug-pull defense). **MCP gateways** as a central policy point for authentication, scoping, rate limits, logging and tool-description inspection. OAuth 2.1 for remote MCP servers, with short-lived, narrowly scoped tokens and no token passthrough. **Secrets management:** credentials never enter the model's context and are injected by the harness at call time from a vault. Sandboxed execution and network egress controls for tools that run code. Monitoring and red-teaming the tool layer. Builds on, without repeating, `04` Module 03 (MCP auth basics), `04` Module 09 (least privilege, approval gates, sandboxing) and `08` Module 08 (data and tool authorization, audit logging).
  - *System Bottlenecks & Focus:* Defense in depth without approval fatigue or crippling latency. The focus is a reference architecture (registry → gateway → scoped credentials → sandbox → audit log) that a candidate can draw and defend in a system-design round.

- **Module 08: Common Failure Modes & Best Practices**
  - *Key Concepts:* Context failures: over-stuffing, cache invalidation from dynamic prefixes, compaction that silently drops a critical constraint, stale or poisoned memory files, sub-agents returning lossy summaries, and tool-definition bloat. Interop failures: A2A tasks with no timeout or cancellation path, and trust assumed rather than verified. Security failures: approval fatigue, over-broad OAuth scopes, unpinned tool definitions, secrets in logs or traces, and unaudited third-party skills. Each with a detection signal and a concrete fix, plus a pre-launch checklist for a production agent.
  - *System Bottlenecks & Focus:* Silent degradation. Most of these failures cause no error, only worse answers, higher bills or a widened attack surface. The focus is the signals that catch them early.

- **Short/long-term memory, memory summarization triggers, episodic vs semantic memory** → `04_ai_agents_and_protocols` Module 04. This topic's Modules 03–04 cover the caching trade-off and the harness patterns around that memory, not memory types themselves.
- **Graph orchestration, durable execution, checkpoints, human-in-the-loop interrupts** → `04` Module 05. Referenced in Module 04 as building blocks.
- **Multi-agent architectures** → `04` Module 06. Module 04 covers sub-agents only as a context-isolation technique and its token cost.
- **MCP architecture, primitives, basic auth and tool-level permissions** → `04` Module 03. Modules 06–07 cover supply-chain threats and production defenses on top of it.
- **Indirect injection, least privilege, approval gates, sandboxing, auditing (agent level)** → `04` Module 09. **Direct injection and jailbreaks** → `05` Module 08. Module 06 covers injection only as a supply-chain delivery path.
- **Context budget allocation, ordering, "lost in the middle"** → `05` Module 06. Module 02 covers length-driven degradation, not position bias.
- **KV cache, prefix caching and PagedAttention mechanics** → `06_llm_inference_and_optimization`. Module 03 covers provider-level caching economics and layout, not the serving internals.
- **Data and tool authorization, trust boundaries, compliance and audit architecture** → `08_genai_system_design_and_llmops` Module 08. Module 07 builds the tool-supply-chain layer on top of it.
