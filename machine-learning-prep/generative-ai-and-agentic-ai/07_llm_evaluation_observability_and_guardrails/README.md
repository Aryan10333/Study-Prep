# LLM Evaluation, Observability & Guardrails Syllabus

## 1. Context & Alignment
* **Profile Focus:** Directly targets the evaluation, monitoring, and safety-engineering dimensions of production LLM systems — a distinct discipline from `05_prompt_engineering_and_structured_generation`'s prompt-level concerns and `06_llm_inference_and_optimization`'s serving-infrastructure concerns. Where those topics asked "how do I get a good response efficiently," this topic asks "how do I know whether the response was actually good, catch it when it wasn't, and prevent the system from doing real harm."
* **Interview Frequency:** High and rising, especially for Applied/Platform/MLOps-adjacent roles — "how would you evaluate an LLM feature before shipping it," "how do you catch hallucinations in production," "walk me through your LLM observability stack," and "how would you design guardrails for a customer-facing chatbot" are now standard screens, distinct from pure prompt-engineering or inference-optimization questions.
* **Core Goal:** Build a precise, engineering-grounded model of how real LLM systems get evaluated (automated metrics, LLM-as-judge, human preference data), monitored in production (tracing, logging, drift detection), and protected against real failure modes (hallucination, unsafe output, factual error) — so a candidate can design a defensible, measurable evaluation and safety strategy rather than reciting tool names.

## 2. Module Chapters & Conceptual Scope

- **Module 01: Why LLM Evaluation Is Fundamentally Hard**
  - *Key Concepts:* Non-determinism and open-ended generation mean there's rarely a single correct output to compare against; the real gap between "the metric moved" and "the system actually got better"; why evaluation metrics themselves need validation (do they correlate with real human judgment/task success?) before being trusted. Established taxonomy: reference-based vs. reference-free, automated vs. human, offline vs. online evaluation.
  - *System Bottlenecks & Focus:* Establishing the core epistemic problem — measuring quality for a system whose "correct" output space is often unbounded — that every later module's technique is a real, partial answer to.

- **Module 02: Automated Reference-Based & Reference-Free Metrics**
  - *Key Concepts:* Classical reference-based metrics (BLEU, ROUGE, BERTScore) and what they actually measure (surface/embedding overlap) vs. what they're often assumed to measure (semantic correctness). Reference-free signals — **perplexity and self-consistency — treated as measuring genuinely different, narrower properties, not presented as interchangeable general-purpose quality metrics**: perplexity reflects the model's own fluency/predictability under its own distribution, not correctness; self-consistency reflects real answer stability across samples, not real factual accuracy (a model can be consistently wrong). The real, well-documented failure modes of each metric class (a fluent, wrong answer can score well; a correct-but-differently-phrased answer can score poorly).
  - *System Bottlenecks & Focus:* Real metric-validity risk — using an ill-suited metric for a given task, or treating a narrow signal (perplexity, self-consistency) as a general quality measure, can produce misleading offline signal that doesn't correlate with real production quality.

- **Module 03: LLM-as-a-Judge — Design, Biases & Calibration**
  - *Key Concepts:* Using a real LLM to evaluate another LLM's outputs at scale; documented real judge biases (position bias, verbosity bias, self-preference bias where a model favors outputs resembling its own style). **Judge reliability as a distinct concern beyond bias**: a judge can be genuinely low-bias yet still disagree with real human judgments, be poorly calibrated (its scores don't track real quality linearly), or be unstable — producing meaningfully different scores under small rubric or prompt-wording changes. Rubric design for judge prompts; calibrating judge scores against real human-agreement baselines, and validating judge *stability* across rubric/prompt variants, before trusting a judge in production.
  - *System Bottlenecks & Focus:* The real trade-off between LLM-as-judge's scalability and its documented, real bias *and* reliability risks — and the concrete techniques (randomized ordering, rubric grounding, calibration checks, stability testing) that mitigate each separately.

- **Module 04: Human Evaluation & Preference Data Collection**
  - *Key Concepts:* Rubric design for human annotation tasks; inter-annotator agreement (Cohen's/Fleiss' kappa) as a real measure of rubric/task clarity, not just annotator quality; collecting pairwise preference data for RLHF/DPO-style training; real cost/scalability trade-offs of human evaluation vs. automated approaches.
  - *System Bottlenecks & Focus:* Human evaluation as the real ground-truth anchor other methods (Module 02's metrics, Module 03's LLM-judges) ultimately get validated against — and the real, practical constraints (cost, latency, consistency) that limit how much of it any system can afford.

- **Module 05: RAG & Agent-Specific Evaluation**
  - *Key Concepts:* Evaluation dimensions specific to retrieval-augmented systems — faithfulness/groundedness (does the answer follow from retrieved content), answer relevance, context precision/recall; evaluation dimensions specific to agentic systems — trajectory correctness, tool-call accuracy, task-completion rate across multi-step real executions, **evaluated alongside real agent efficiency metrics, not correctness alone: tool-call count, token usage, wall-clock latency, and real cost per completed task** — a production agent that succeeds via an excessive number of real tool calls or an inflated token budget is a genuinely different (and generally worse) outcome than one that succeeds efficiently. Explicit boundary: this module evaluates RAG/agent *system output quality and efficiency*, not `03_advanced_rag`'s retrieval-pipeline construction or `04_ai_agents_and_protocols`'s agent-architecture design.
  - *System Bottlenecks & Focus:* Why single-turn, single-output metrics (Modules 02-03) are insufficient for multi-step or retrieval-grounded systems, and why real task-success rate alone is an incomplete production evaluation without also tracking the real efficiency cost of reaching that success.

- **Module 06: Hallucination Detection & Factuality Evaluation**
  - *Key Concepts:* A real taxonomy of hallucination types (factual fabrication, contradiction of provided context, unsupported extrapolation); detection techniques — self-consistency-based checks, retrieval-grounded verification, NLI/entailment-based fact-checking against source content. **Self-consistency explicitly qualified as a real hallucination *signal*, not a *detector*: a model can produce the same incorrect answer consistently across samples, so agreement-across-samples alone cannot confirm real factual correctness — genuine factuality verification requires an external or retrieval-grounded check against real source content**, not the model's own repeated agreement with itself. Real, honest limits of each detection approach (no technique catches every hallucination type).
  - *System Bottlenecks & Focus:* Turning "the model sometimes makes things up" into a measurable, monitorable real production signal rather than an unquantified risk — while being precise about which techniques (self-consistency) are cheap-but-partial signals versus which (retrieval/NLI-grounded checks) are genuine, if costlier, detectors.

- **Module 07: Observability — Tracing, Logging & Structured Monitoring for LLM Systems**
  - *Key Concepts:* Distributed tracing and spans for multi-step LLM pipelines (a single user request touching retrieval, multiple model calls, tool use); structured logging of prompts/completions/metadata for real debuggability; production monitoring dashboards tracking real quality/cost/latency signals together. **Explicit ownership boundary, kept precise**: this topic owns real *pipeline-level* tracing, logging, quality signals, and debugging — which specific step or call in a multi-step pipeline produced a bad output, and why; `06_llm_inference_and_optimization` Module 09 owns real *infrastructure-level* serving metrics (TTFT, TPOT, GPU/memory utilization) — this module references those only as inputs a pipeline-level trace might display alongside quality signals, never re-deriving how they're computed.
  - *System Bottlenecks & Focus:* Why a multi-step LLM pipeline's real failure often can't be diagnosed from aggregate metrics alone — tracing/logging is what makes a specific real failure's root cause (which step, which call) actually findable, distinct from infrastructure-level performance monitoring.

- **Module 08: Guardrails & Content Safety Classification**
  - *Key Concepts:* A production guardrail is a real, three-stage **detection → decision → enforcement** pipeline, not classification alone: detection (input/output safety classifiers — toxicity, PII, bias, unsafe-content detection), decision (a real policy mapping a detected signal to an action, often with a real confidence threshold), and enforcement (allow / block / rewrite / fallback-response — genuinely different real remediation strategies with different user-experience and safety trade-offs). Guardrail architecture patterns (pre-generation input checks, post-generation output checks, streaming-safe validation); real, honest limits of classifier-based detection (false positive/negative trade-offs, adversarial evasion). **Real latency/cost trade-offs of guardrails**: each additional safety check (especially a real second-model classifier call) adds real, measurable latency and cost to every request — a production guardrail stack has to be evaluated on this trade-off explicitly, not assumed free. Explicit boundary: this module covers safety *classification, decisioning, enforcement, and evaluation*, not `05_prompt_engineering_and_structured_generation` Module 08's prompt-level injection-defense techniques (delimiters, system-prompt hardening) — referenced only where they interact with guardrail evaluation, not re-derived.
  - *System Bottlenecks & Focus:* The real precision/recall trade-off every content-safety classifier makes, the real decision/enforcement-policy design that turns a detection signal into a production action, the real latency/cost budget guardrails consume, and why guardrails are a real, additional layer alongside (not a replacement for) prompt-level defenses.

- **Module 09: Production Evaluation Pipelines — Continuous Evaluation, Regression Testing & Drift Detection**
  - *Key Concepts:* CI/CD-style continuous evaluation for model/system-level changes (a new model version, a new retrieval index, a new tool) — distinct from `05_prompt_engineering_and_structured_generation` Module 07's prompt-template-level A/B testing and versioning; regression test suites for LLM systems. **Evaluation-set/configuration versioning and reproducibility as a real prerequisite, not an afterthought**: a continuous-evaluation result is only trustworthy if the real evaluation dataset, model version, prompt/configuration, and evaluator (metric or judge) version are all tracked together — an unversioned change in any one of these can produce a real, misleading apparent quality shift that has nothing to do with the actual system change being tested. **Real drift explicitly split into distinct types, each with its own detection method and remediation**: input/data drift (the real distribution of incoming requests changes), output/quality drift (real output quality degrades for a stable input distribution), and model/behavior drift (the underlying model's real behavior changes, e.g. after a silent provider-side update) — conflating these leads to the wrong real remediation being applied. Canary releases and rollback triggers for LLM-system changes specifically.
  - *System Bottlenecks & Focus:* Turning every earlier module's evaluation technique into a real, automated, continuously-running production process rather than a one-time offline check — one that stays trustworthy only when its own inputs (dataset, config, evaluator) are versioned, and that diagnoses the real, specific type of drift rather than treating all quality regressions as the same problem.

### Cross-Module Boundary Discipline
This topic deliberately avoids re-deriving content already owned by prior topics:
- **Prompt-level A/B testing, prompt versioning, and prompt regression testing** → `05_prompt_engineering_and_structured_generation` Module 07 — this topic covers model/system-level continuous evaluation (Module 09), not prompt-template-specific testing workflows.
- **Prompt injection/jailbreak defense techniques (delimiters, system-prompt hardening, input/output filtering as a prompt-layer defense)** → `05_prompt_engineering_and_structured_generation` Module 08 — this topic's Module 08 covers safety *classification and evaluation* as a distinct, additional layer, referencing prompt-layer defenses only where they interact with guardrail evaluation.
- **RAG retrieval-pipeline construction (chunking, embeddings, hybrid search)** → `03_advanced_rag` — this topic's Module 05 evaluates RAG *output quality* (faithfulness, relevance), not retrieval-pipeline mechanics.
- **Agent architecture and orchestration** → `04_ai_agents_and_protocols` — this topic's Module 05 evaluates agent *trajectory/task-completion correctness*, not agent-system design.
- **Inference-time cost/latency monitoring metrics (TTFT, TPOT, GPU utilization)** → `06_llm_inference_and_optimization` Module 09 — this topic's Module 07 covers LLM-*pipeline* observability (tracing, structured logging, quality signals), not inference-serving infrastructure metrics.

This topic owns: how to measure whether an LLM system's real output is actually good, how to see what's happening inside a real production LLM pipeline when it isn't, and how to prevent and detect real, harmful or incorrect output before and after it reaches a user.
