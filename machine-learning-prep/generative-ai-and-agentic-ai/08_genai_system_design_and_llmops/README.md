# GenAI System Design & LLMOps Syllabus

## 1. Context & Alignment
* **Profile Focus:** Directly targets the "AI System Design" interview format explicitly named in the candidate's own curriculum weighting — the discipline of taking everything built in prior topics (retrieval in `03_advanced_rag`, agents in `04_ai_agents_and_protocols`, prompting in `05_prompt_engineering_and_structured_generation`, serving in `06_llm_inference_and_optimization`, evaluation/observability/guardrails in `07_llm_evaluation_observability_and_guardrails`) and composing it into one coherent, defensible, whiteboard-able production architecture, plus the operational discipline (LLMOps) that keeps that architecture running, versioned, and safely changeable over time.
* **Interview Frequency:** High for Mid/Senior Applied AI Engineer, AI Platform Engineer, and ML Engineer screens specifically — "design a RAG-based customer support assistant," "design ChatGPT," "design a coding copilot," "how would you roll out a new model version safely," and "walk me through your LLMOps pipeline" are now standard system-design-round questions, structurally different from the component-level deep-dives the prior topics each cover.
* **Core Goal:** Build a repeatable framework for approaching a GenAI system-design interview (requirements gathering, capacity estimation, architecture selection, trade-off articulation) and a precise, engineering-grounded model of LLMOps (versioning, CI/CD, deployment strategy, reliability engineering, security/compliance) — so a candidate can design and defend a production GenAI system end-to-end, explicitly composing prior topics' components rather than re-deriving them.

## 2. Module Chapters & Conceptual Scope

- **Module 01: The GenAI System Design Interview Framework**
  - *Key Concepts:* A repeatable, real interview approach — clarifying functional requirements (what must the system do) and non-functional requirements (latency budget, availability target, cost ceiling, data-freshness requirement) before proposing any architecture; back-of-envelope capacity estimation as a first-class interview skill, not an afterthought; structuring a whiteboard answer (requirements → high-level architecture → deep-dive on 1-2 bottleneck components → trade-offs and failure modes) rather than jumping straight to a solution. Real, common interviewer probes (scale changes, a component fails, cost must drop 10x) and how a structured framework survives them.
  - *System Bottlenecks & Focus:* The real risk this module addresses isn't a missing technique — it's an unstructured answer that either over-engineers a solution to unstated requirements or misses a stated constraint entirely; a repeatable framework is what keeps a 30-45 minute answer coherent under real interviewer pressure.

- **Module 02: Reference Architectures for Common GenAI System Design Questions**
  - *Key Concepts:* A tight, deliberately limited set of real, recurring GenAI system archetypes — **RAG-based Q&A/search assistant, agentic task-completion system, real-time interactive LLM service, and batch/offline generation pipeline** — each with its own real architecture diagram, component list, and dominant bottleneck. On-device/cloud-hybrid deployment is covered as a real *variant* applied to one of these four archetypes when relevant (e.g., a real-time service with an on-device fallback), not a fifth standalone archetype — kept deliberately tight to avoid the real risk of shallow, memorized coverage across too many named patterns. Explicit composition, not re-derivation: each archetype's retrieval layer references `03_advanced_rag`'s own retrieval-pipeline content, its agent layer references `04_ai_agents_and_protocols`'s own architecture content, and its serving layer references `06_llm_inference_and_optimization`'s own serving-infrastructure content, as already-built components being assembled, not re-explained from scratch.
  - *System Bottlenecks & Focus:* Recognizing which real archetype (or archetype-plus-variant) a given prompt maps to, and which component in that archetype is the actual bottleneck worth deep-diving on in an interview's limited time, rather than giving equal shallow coverage to every box in the diagram.

- **Module 03: Capacity Estimation, Traffic Modeling & Cost Engineering**
  - *Key Concepts:* Real back-of-envelope math for GenAI systems specifically — **QPS-to-GPU-count estimation done as a real, multi-assumption derivation, not a direct conversion**: real request rate, real input/output token counts per request, a stated concurrency level per GPU (how many in-flight requests a replica can serve, itself a function of `06_llm_inference_and_optimization`'s own batching/serving content, referenced not re-derived), a stated utilization target (real GPUs are never provisioned at 100% planned utilization), and a real latency/SLO constraint that caps how much request queuing is tolerable — each assumption made explicit rather than left implicit in a single "QPS ÷ throughput" shortcut. Storage sizing for a vector index at a given corpus size and embedding dimension; peak-vs-average traffic provisioning. **Cost engineering built directly on `06_llm_inference_and_optimization` Module 09's own GPU-time-based cost model, referenced not re-derived**: this module's own new content is the system-level question of *build vs. buy* (self-hosted GPU serving vs. a hosted API) and *how cost scales with real growth assumptions*, not the underlying per-request cost formula itself. **Two real, explicitly distinct caching layers, never conflated**: semantic response caching (caching a full generated answer keyed on query similarity — a direct cost/latency win, but with real correctness risk if a stale or near-but-not-identical query returns a wrong cached answer, and real privacy risk if a cached response leaks across users/tenants) versus retrieval/index caching (caching embedding lookups or retrieved chunks — a different real staleness profile tied to knowledge-base update frequency, not query semantics) — each with its own real invalidation strategy and risk profile.
  - *System Bottlenecks & Focus:* The real gap between a system that works in a demo and one whose cost and capacity have actually been sized against real, stated traffic and concurrency assumptions — and the specific real levers (the two distinct caching layers, batching-aware capacity planning, build-vs-buy) that move that number, each with its own real trade-off, not a free win.

- **Module 04: Data & Knowledge Infrastructure at Scale**
  - *Key Concepts:* Vector database deployment architecture — sharding and replication strategies, index-rebuild vs. incremental-update trade-offs, and real freshness/staleness budgets for a knowledge base that changes over time. **The full real knowledge-base lifecycle, not just ingestion and freshness**: data ingestion/ETL pipeline design for keeping a RAG knowledge base or fine-tuning dataset current; **deletion propagation** (a real, often-missed requirement — when a source document is deleted or a user requests erasure, its vectors/chunks must actually be removed from every index copy, not just the source); **re-indexing and versioning** (a real index version is a point-in-time snapshot, and a bad re-index needs a real rollback path back to the previous version); and **multi-tenant isolation** (real enterprise RAG systems must guarantee one tenant's documents are never retrievable by another tenant's queries, a real index-partitioning or metadata-filtering requirement, not an assumption). Explicit boundary: this module covers real infrastructure *operations* around a vector store and data pipeline (deployment topology, scaling, freshness, lifecycle), not `03_advanced_rag`'s own chunking/embedding/hybrid-search *algorithm* content, which is referenced as an already-built layer running on top of this infrastructure.
  - *System Bottlenecks & Focus:* The real operational question "how does the knowledge base stay correct, current, deletable, and tenant-isolated as data and traffic both grow," distinct from the retrieval-quality question of "how does the retrieval algorithm find the right chunk," which is a separate, already-owned concern.

- **Module 05: LLMOps Foundations — Versioning, Registries & CI/CD Pipeline Architecture**
  - *Key Concepts:* The real operational pipeline that turns an already-defined evaluation into an enforced production gate — the real flow of **versioned inputs → evaluation execution → quality gate → approval → deployment → recorded lineage** — distinct from the evaluation methodology itself. Model and prompt registries (what artifact is deployed where, with what version); CI/CD pipeline architecture for GenAI systems (build → automated-eval gate → staged deployment); environment topology (dev/staging/prod parity for a system with real, expensive GPU dependencies). **Real artifact lineage as a first-class concern**: a production result is only fully explainable if the *combination* of model version, prompt version, evaluator version, dataset/index version, and deployment-config version that produced it is jointly recorded — knowing only "which model" without also knowing "which prompt, which evaluator, which index snapshot" makes real rollback and debugging unreliable. Explicit boundary: `05_prompt_engineering_and_structured_generation` Module 07 owns prompt-template-level A/B testing and versioning *methodology*, and `07_llm_evaluation_observability_and_guardrails` Module 09 owns continuous-evaluation *methodology* (what gets measured, how drift is diagnosed) — this module owns the real operational pipeline and artifact-lineage recording around those already-defined evaluation results, not the tests or metrics themselves.
  - *System Bottlenecks & Focus:* The real operational gap between "we have a way to evaluate a change" (prior topics) and "a change cannot reach production without automatically passing that evaluation, and its full lineage is recorded when it does" (this module) — CI/CD and lineage tracking as the enforcement and accountability mechanism, not the evaluation logic.

- **Module 06: Deployment Strategies, Progressive Rollout & Experimentation Infrastructure**
  - *Key Concepts:* Real deployment patterns for GenAI system changes — blue-green deployment, canary releases with real traffic-percentage ramping, and shadow deployment (running a new model/prompt/pipeline version against real production traffic without serving its output) — each with a genuinely different real risk/speed trade-off. Feature-flag infrastructure for gating a GenAI feature independent of code deployment; the real infrastructure for routing a percentage of traffic to a variant and collecting outcome data, which `07_llm_evaluation_observability_and_guardrails`'s own continuous-evaluation methodology then scores. **Explicit promotion, rollback, and abort criteria as a required part of any rollout design, not an implied afterthought**: real, stated thresholds across quality (from Topic 07's own evaluation signals), latency, error rate, safety/guardrail-flag rate, and cost, each independently capable of halting a canary's ramp or triggering an automatic rollback — a rollout plan without these stated triggers isn't actually reversible in practice, only in principle.
  - *System Bottlenecks & Focus:* The real, asymmetric cost of a bad rollout in a GenAI system (a regressed prompt or model version can silently degrade quality for real users before an aggregate metric catches it) — and why progressive, reversible rollout strategies, gated by explicit promotion/rollback/abort criteria across multiple real signal types, exist specifically to bound that real blast radius.

- **Module 07: Reliability Engineering — Redundancy, Fallbacks & Multi-Provider Architecture**
  - *Key Concepts:* Real failure modes specific to GenAI systems — a model provider outage, a rate-limit exhaustion, a degraded-latency incident on a single dependency — and the real architecture patterns that bound their blast radius: circuit breakers, provider fallback chains, request queuing and backpressure under real load, and graceful degradation (a lower-quality but available response beats no response). **Real retry, idempotency, and timeout policy as a required companion to circuit breakers/fallbacks, not a redundant afterthought**: naive retries under a real provider degradation can cause a retry storm that worsens the very outage being retried against, and a retried request that triggers a real side effect (a tool call, a database write, a sent email) without an idempotency key can duplicate that side effect — a genuinely distinct and common real failure mode for tool-using agentic systems specifically, requiring its own explicit real design (idempotency keys, bounded retry budgets with backoff, and stated per-call timeouts). **Provider fallback framed with its real capability trade-offs stated explicitly, not just availability**: a secondary fallback model can have a genuinely different real context-window limit, prompt-format compatibility, output quality, and safety behavior than the primary — a fallback is a real quality/capability degradation accepted in exchange for availability, and a system design should state that trade-off rather than treat the fallback as a transparent, equivalent substitute.
  - *System Bottlenecks & Focus:* Real availability engineering for a system with an inherently less reliable dependency (a third-party model API, or a GPU fleet under real contention) than a typical stateless microservice — designing for that dependency's real failure (including the real risk that a naive retry makes it worse, and that a fallback is a real capability trade rather than a free substitute), not assuming any of it away.

- **Module 08: Security, Privacy & Compliance Architecture for GenAI Systems**
  - *Key Concepts:* Real system-level security architecture — authentication *and, distinctly, authorization* for GenAI APIs. **Authorization treated explicitly at the data/tool level, not just the API-endpoint level**: the real, enterprise-critical question isn't only "is this caller authenticated," it's "which specific documents may this user's RAG query retrieve, and which specific tools may this user's agent invoke" — a real per-user/per-tenant data- and tool-scoping requirement (least-privilege access control), distinct from and layered on top of ordinary API authentication. Secrets/API-key management, encryption in transit and at rest, data residency and retention policy design, and audit logging infrastructure for real compliance requirements (SOC2/GDPR-style obligations). **Real architecture-level control points for sensitive-data leakage, indirect prompt injection, and unsafe tool access named explicitly**, even though their detailed defenses are owned elsewhere: where in the architecture could retrieved private data leak into a response meant for a different, unauthorized user; where could untrusted retrieved or tool-returned content carry an indirect injection payload into the model's context; where must a tool-invocation boundary enforce the same least-privilege authorization as data retrieval — named as real architectural control points a system design must show, with the detection/defense techniques themselves referenced from `05_prompt_engineering_and_structured_generation` (injection defense) and `07_llm_evaluation_observability_and_guardrails` (content-level detection), not re-derived here. Explicit boundary, stated precisely because the word "PII" appears in multiple places: `07_llm_evaluation_observability_and_guardrails` Module 08 owns *content-level* PII/toxicity *detection* (a classifier inspecting a specific request/response's content); this module owns *system-level* data governance and access control (where data is stored, who and what may access it, how long it's retained, how access is audited) — a genuinely different layer, referenced as a downstream consumer of that content-level detection signal, not a re-implementation of it.
  - *System Bottlenecks & Focus:* The real, often-interview-tested question of how a GenAI system's data-handling and access-control architecture (not its content-safety classifiers) satisfies real enterprise security/compliance requirements — least-privilege data/tool authorization, encryption, retention, auditability, and named architectural control points for leakage/injection/unsafe-tool-access as system-design concerns in their own right.

- **Module 09: End-to-End GenAI System Design Case Studies**
  - *Key Concepts:* 2-3 full, real worked system-design walkthroughs (e.g., a RAG-based enterprise knowledge assistant, an agentic coding copilot) applying Module 01's framework in order — requirements, architecture selection (Module 02), capacity/cost (Module 03), data infrastructure (Module 04), LLMOps/CI-CD (Module 05), deployment strategy (Module 06), reliability (Module 07), and security (Module 08) — as one coherent, defensible design, explicitly composing every prior topic's already-built components (retrieval, agents, serving, evaluation, guardrails) rather than re-deriving any of them. **Each case study explicitly time-boxed to a real 30-45 minute interview shape**: requirements gathering, capacity/architecture sketch, one or two genuine deep-dives on the system's actual bottleneck (not shallow, equal-depth coverage of every component), and a closing trade-offs/failure-modes discussion — modeling the real, uneven time allocation an actual interview demands, not an exhaustive textbook coverage of all 8 modules at equal depth.
  - *System Bottlenecks & Focus:* Synthesis under real interview time constraints — demonstrating that a candidate can move fluidly across all 8 preceding modules' concerns within one coherent, realistically time-boxed answer, correctly prioritizing which trade-offs and which one or two deep-dives matter most for the specific system being asked about.

Module 10 (Interview Q&A track — Track 3) will follow once Tracks 1 and 2 are complete and signed off, per the established 3-track pipeline.

### Cross-Module Boundary Discipline
This topic deliberately avoids re-deriving content already owned by prior topics — it is explicitly a composition/synthesis topic, not a new component topic:
- **RAG retrieval-pipeline construction (chunking, embeddings, hybrid search, reranking)** → `03_advanced_rag` — this topic's Modules 02 and 04 reference retrieval as an already-built layer, covering its *deployment/scaling infrastructure* and its role in a *whole-system architecture*, not the retrieval algorithm itself.
- **Agent architecture, orchestration, MCP, tool calling** → `04_ai_agents_and_protocols` — referenced in Module 02 and Module 09 as an already-built component being composed into a larger system, not re-explained.
- **Prompt-template-level A/B testing, prompt versioning, prompt regression testing, and prompt-injection/jailbreak defense** → `05_prompt_engineering_and_structured_generation` Modules 07-08 — this topic's Module 05 covers the CI/CD *infrastructure* that runs already-defined prompt tests, not the testing methodology itself.
- **Inference-serving mechanics (vLLM, quantization, KV cache, batching, TTFT/TPOT) and its own cost model** → `06_llm_inference_and_optimization` — this topic's Module 03 builds directly on that topic's own cost model for system-level capacity/build-vs-buy decisions, without re-deriving per-request cost math.
- **Evaluation methodology, LLM-as-judge, hallucination detection, pipeline tracing/observability, content-safety guardrail classification, and continuous-evaluation/drift-detection methodology** → `07_llm_evaluation_observability_and_guardrails` — this topic's Modules 05-06 cover the deployment/CI-CD *infrastructure* that gates on and consumes those already-defined evaluation results, not the evaluation techniques themselves.

This topic owns: how to structure a GenAI system-design interview answer, how to compose prior topics' components into a coherent whole-system architecture, how to size and cost that system, and the LLMOps discipline (versioning, CI/CD, deployment, reliability, security) that keeps it running safely in production.
